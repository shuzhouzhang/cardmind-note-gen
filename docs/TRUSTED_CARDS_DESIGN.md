# 可信知识卡：个人功能设计练习

状态：`提案阶段，尚未实现`

这份文档定义一个适合你亲自完成的 CardMind 功能。它不是用来包装已有代码，而是让你经历一次真实的需求分析、方案选择、实现和验证。

## 1. 当前状态

用户可见的 `knowledge_cards` 已保存：

- `sourceType`
- `sourceRef`
- `sourceTitle`
- `sourceSnippet`

结构化 `cm_*` 知识引擎还支持来源消息、置信度和 `active/quarantine/archived` 状态，但 UI 制卡链路没有完整复用这些机制。

因此目前可以看到一段来源摘要，却还不能稳定回答：

- 这张卡片精确来自原文哪里？
- 模型对这张卡片有多确定？
- 低可信卡片为什么会或不会出现在图谱中？
- 同一段内容重复生成时如何识别重复卡片？

## 2. 目标

让每张 AI 生成卡片具备：

1. 可定位的原始来源。
2. 明确的置信度。
3. 可解释的审核状态。
4. 稳定的去重依据。
5. 从卡片返回原始记录的入口。

## 3. 三种方案

### 方案 A：保持现状

继续只保存 `sourceSnippet`。

- 优点：不需要数据库迁移，改动最小。
- 缺点：摘要可能重复，不能精确定位，也不能隔离低可信内容。

### 方案 B：扩展 `knowledge_cards`

给现有卡片增加来源定位、置信度、状态和稳定键。

- 优点：可以分阶段完成，直接改善当前 UI。
- 缺点：继续维护两套知识模型，以后还需要迁移。

### 方案 C：让 UI 直接使用 `cm_*` 知识模型

把生成、审核、图谱和来源统一到结构化知识引擎。

- 优点：长期数据模型更清晰，来源和关系天然统一。
- 缺点：改动面大，可能同时影响生成、图谱、复习和旧数据。

## 4. 推荐路线

先采用方案 B 完成一个可验证的垂直切片，再为方案 C 写迁移设计。

第一阶段只处理：

```text
生成一张卡片
  -> 保存精确来源和置信度
  -> 低置信度进入待确认
  -> UI 展示依据并可回到来源
  -> 测试验证
```

不要在第一阶段同时重写整个图谱和 Python 引擎。

## 6. 建议数据模型

字段名称可以调整，但每个字段必须有明确用途：

| 字段 | 用途 |
|---|---|
| `confidence` | 模型或规则给出的可信度 |
| `status` | `active`、`quarantine` 或 `archived` |
| `sourceLocatorJson` | 消息 ID、文件路径、锚点或字符范围 |
| `canonicalKey` | 幂等和去重使用的稳定键 |
| `reviewReason` | 为什么需要人工确认 |

数据库迁移必须兼容已有卡片：旧数据不能因为新字段而无法读取。

## 7. 最小实现顺序

1. 给 TypeScript 类型增加新字段。
2. 给 SQLite 初始化或迁移逻辑增加字段。
3. 修改生成 JSON 约束和解析校验。
4. 写入卡片时保存来源定位、置信度和状态。
5. 查询时区分活动卡片与待确认卡片。
6. 卡片详情显示来源和审核原因。
7. 增加“查看原文”和“确认卡片”动作。
8. 补充自动化测试和一次真实演示。

## 8. 验收标准

- 相同来源重复生成不会静默产生重复活动卡片。
- 低于阈值的卡片不会直接进入活动图谱或复习队列。
- 每张新卡片可以定位到原始消息或文档位置。
- 模型缺少必填字段或返回非法 JSON 时不写入脏数据。
- 旧卡片升级后仍能正常打开和复习。
- 卡片分块测试、知识引擎测试和 TypeScript 类型检查全部通过。

## 9. 面试讲法模板

> 我发现原来的卡片只保存来源摘要，用户无法稳定追踪到原文，低可信结果也缺少隔离。我比较了继续扩展旧表和直接统一到结构化知识模型两种方案。为了控制迁移风险，我先在现有 UI 链路实现来源定位、置信度和待确认状态，同时保留后续统一模型的迁移空间。验证覆盖了低置信度隔离、重复生成、非法 JSON 和旧数据兼容。
